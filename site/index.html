BUILD 05 · THINGS ESCALATED

It started with Minecraft. That didn’t last long.

Minecraft became the excuse. The real project became learning how to build and operate software with AI as a genuine collaborator.

  1. Minecraft

    Host a private Java server for family and friends.

  2. Docker

    Make the services isolated, repeatable, and manageable.

  3. API

    Expose server status and persist useful world data.

  4. Custom plugin

    Save locations directly from inside the game with /mark.

  5. World Atlas

    Search, view, copy, rename, and manage saved locations.

  6. AI engineering system

    Add standards, verification rules, operational scripts, pull requests, documentation, and human review.

I stopped treating AI like a chatbot and started treating it like a teammate. That teammate needed context, standards, feedback, verification, and the occasional firm disagreement.

BUILD 06 · REALITY CHECK

Things did not go according to plan.

Which was useful, because the failures taught me more about working with AI than the clean wins did.

01

The token leak.

While verifying documentation, the AI printed a live Atlas token into the session.

We rotated the credential, documented the failure mode, removed the unnecessary shell export, and built a tested rotation script so the fix became repeatable.

Lesson Security mistakes need systems, not apologies.

02

Localhost lied.

Several documented health checks failed even though every service was healthy.

Inside the containers, localhost resolved to IPv6 while the services were listening on IPv4. The commands looked right. Running them proved otherwise.

Lesson Exact verification beats plausible commands.

03

The test passed. The feature did not.

An authentication check compared a container’s token against the same container’s running configuration.

It could report success without proving rotation worked. We rebuilt the test using independently sourced values and confirmed the old token was rejected.

Lesson A passing test can still test the wrong thing.

04

The safety check had a hole.

A preflight script claimed to detect committed private keys, but its grep pattern was being interpreted as command options.

The bug only surfaced because we tested the security tool against deliberately bad input instead of running it solely against a clean repository.

Lesson Security tooling needs known-bad tests.
AI was confidently wrong sometimes.

So was I.

The useful part was building a workflow where neither of us got the final word without evidence.

BUILD 08 · WHY OBVIOUS

I realized I had been building toward Obvious without knowing it.

When I first read your job description, three phrases stopped me.

  • Memory.
  • Agent-to-agent collaboration.
  • Non-deterministic repeatability.

At first, I thought they were simply interesting technical problems.

Then I looked back at what I had spent the last few weeks building. Without realizing it, I had been obsessing over those exact ideas.

The more I worked with AI, the less I cared about writing better prompts. I became fascinated by building better systems around AI.

  • Shared documentation
  • Operating instructions
  • Verification
  • Engineering standards
  • Feedback loops

I stopped trying to build smarter AI. I started trying to build smarter environments for AI to work inside.

That is what made your job description feel different.

Not because you mentioned AI. Because you described the problems that appear after the novelty wears off.

Memory. Repeatability. Collaboration. Real products.

Those are the problems I want to spend years solving.

BUILD 09 · ONE IDEA

I had one. I’m holding it.

While building this, I kept coming back to something from chapter six.

Every failure in that chapter looked like a success first. The health check reported healthy. The rotation test passed. The security script said the repository was clean.

None of them were wrong about what they measured. They were wrong about what I assumed they measured.

Finished AI work gives me the same feeling. Confident, well formatted, and quiet about which parts were actually checked.

I had a specific idea about that. I wrote it out. Then I cut it.

Because I have spent about an hour inside your product, and the people I would be proposing it to have lived in theirs for months. An hour is enough to have an opinion. It is not enough to be worth your time.

So I would rather earn the conversation, use the thing properly, and find out whether the problem I keep hitting is even your problem.

If it is, I would like to talk about it.

BUILD 10 · THE THREAD

It was never the technology.

Everything I have done eventually comes back to communication.

Whether I was supporting engineers at GE in IT and later as a product manager, coaching dads trying to lose weight, volunteering at church, or building software with AI, the technology was never the hardest part.

The hardest part was understanding the problem clearly enough that the right solution became obvious.

That is the part of building I have fallen in love with.

Your team just happens to be solving the most interesting version of that problem I have seen.

AI is not replacing communication. It is making great communication more valuable than ever.

BUILD 11 · THE HONEST PART

Let me save you the guessing.

You are going to check me against your requirements anyway. I would rather do it for you, in both directions, than make you read between the lines.

What I have not done

  • Shipped production React or TypeScript inside a professional engineering team
  • Worked in a codebase serving millions of users
  • Had my frontend code reviewed by senior engineers, daily, at the bar you hire for

That is real. This site is HTML, CSS, and vanilla JavaScript because that is the honest version of what I can build well in a day. Putting React on it would have been a costume.

What I bring on day one

  • More than a decade running enterprise infrastructure — VMware, Linux, Windows, security, and operations
  • Supporting engineers at GE, first in IT and later as a product manager
  • Three products built with AI. Two are live and linked above. The third runs in my house.
  • The engineering standards, verification rules, and human review boundaries an AI coding agent works inside — written by me, because the failures above forced it
  • An API, a custom Java plugin, a dashboard, secure remote access, and a tested token rotation tool, all in use
  • A Marine Corps enlistment, a coaching practice, and a decade in enterprise IT that all came down to the same skill: finding the real problem

React and TypeScript are the part I can learn, and I would rather learn them inside your codebase under real review than claim them on a résumé. I have closed harder gaps on shorter deadlines.

What takes longer to teach is owning an ambiguous problem without a spec, knowing which one is actually worth solving, and telling you plainly when something did not work.

Those came with me. You just read four failures I could have quietly deleted instead.
