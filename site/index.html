BUILD 05 · REALITY CHECK

Things did not go according to plan.

Which was useful, because the failures taught me more about working with AI than the clean wins did.

01

The token leak.

While verifying documentation, the AI printed a live Atlas token into the session.

We rotated the credential, documented the failure mode, removed the unnecessary shell export, and built a tested rotation script so the fix became repeatable.

Lesson Security mistakes need systems, not apologies.

02

Localhost lied.

Several documented health checks failed even though every service was healthy.

Inside the containers, localhost resolved to IPv6 while the services were listening on IPv4. The commands looked right. Running them proved otherwise.

Lesson Exact verification beats plausible commands.

03

The test passed. The feature did not.

An authentication check compared a container’s token against the same container’s running configuration.

It could report success without proving rotation worked. We rebuilt the test using independently sourced values and confirmed the old token was rejected.

Lesson A passing test can still test the wrong thing.

04

The safety check had a hole.

A preflight script claimed to detect committed private keys, but its grep pattern was being interpreted as command options.

The bug only surfaced because we tested the security tool against deliberately bad input instead of running it solely against a clean repository.

Lesson Security tooling needs known-bad tests.
AI was confidently wrong sometimes.

So was I.

The useful part was building a workflow where neither of us got the final word without evidence.

BUILD 07 · WHY OBVIOUS

I realized I had been building toward Obvious without knowing it.

When I first read your job description, three phrases stopped me.

  • Memory.
  • Agent-to-agent collaboration.
  • Non-deterministic repeatability.

At first, I thought they were simply interesting technical problems.

Then I looked back at what I had spent the last few weeks building. Without realizing it, I had been obsessing over those exact ideas.

The more I worked with AI, the less I cared about writing better prompts. I became fascinated by building better systems around AI.

  • Shared documentation
  • Operating instructions
  • Verification
  • Engineering standards
  • Feedback loops

I stopped trying to build smarter AI. I started trying to build smarter environments for AI to work inside.

That is what made your job description feel different.

Not because you mentioned AI. Because you described the problems that appear after the novelty wears off.

Memory. Repeatability. Collaboration. Real products.

Those are the problems I want to spend years solving.
